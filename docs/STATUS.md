# STATUS — Loja Física (bononi-loja)

> Atualizado: 2026-08-26 (5)

## O que é
Dashboard de gestão da **loja física**: acompanhamento de vendas, serviços (pátio e tapeçaria), planograma de gôndola e ordens de **tacógrafo** (com upload de documentos).

- **Supabase:** `vishxwdxqiygbxmtpfoy` (prefixos `loja_` e `taco_`).

## Stack
React + **TypeScript** + Vite + Tailwind + **shadcn/ui** + react-router-dom. Client Supabase padrão (`supabase.from()`, `src/integrations/supabase/client.ts`; `types.ts` gerado, 270KB). Log próprio em `loja_frontend_logs`.

## Telas (rotas em `src/App.tsx`, sob `AppShell`)
- **Vendas:** `/vendas` (visão geral) · `/vendas/vendedores` · `/vendas/sem-faturamento` (lista de vendas paradas p/ o Sardi, `VendasSemFaturamentoTab.tsx`).
- **Serviços:** `/servicos` (resumo) · `/servicos/patio` · `/servicos/tapecaria` · `/servicos/config-colaboradores`.
- **Gôndola:** `/gondola` (controle de preço de etiqueta da gôndola — `GondolaLoja.tsx`, 22KB; **não** é planograma visual, é lista/CRUD com detecção de divergência de preço e impressão de etiqueta).
- **Tacógrafo:** `/tacografo` (lista) · `/tacografo/nova` · `/tacografo/:id` (`TacografoOrdem.tsx`, 37KB — maior tela).
- **Gestão de Serviços** (novo grupo no sidebar, 25-26/08): `/gestao-servicos/distribuicao` · `/gestao-servicos/painel` · `/gestao-servicos/precificacao` · `/gestao-servicos/areas` — as 4 telas funcionais, rodando sobre dados reais (`vw_dist_servicos`/`vw_dist_precificacao`/`vw_dist_colab_area`, publicadas pelo cérebro em 26/08 — ver detalhe abaixo).

## Dados
- **Próprias `loja_`:** `loja_gondola` (planograma), `loja_config_colaborador` (setor/colaborador da loja), `loja_frontend_logs`.
- **Tacógrafo `taco_`:** `taco_ordens`, `taco_anexos`, `taco_cnpj_cards`, `taco_logs`. Storage bucket **`taco-docs`** (upload de documentos, badge automático).
- **Compartilhadas:** `vw_dim_cliente`, `vw_fb_produtos_compras`, dados comerciais (`useComercialData.ts`, `dim-cliente.ts`, `dim-vendedor.ts`).
- **Gestão de Serviços — overlay gravável (`dist_*`):** `dist_areas`, `dist_area_servicop` (código de serviço ERP → área, automático), `dist_colaborador_area` (colaborador → área, Config), `dist_servico` (1 linha por atribuição — distribuir/duplicar/parar/validar), `dist_servico_colaborador`. Tabelas próprias (não replicadas do Firebird). Sem tipagem em `types.ts` (mesmo padrão do Tacógrafo — usa `db = supabase as any` em `src/lib/dist.ts`). Anon/authenticated têm todos os grants, sem RLS (padrão do projeto).
- **Gestão de Serviços — views de leitura (`vw_dist_*`, publicadas pelo cérebro 26/08):** `vw_dist_servicos` (grão = linha de serviço da OS, o que o vendedor lança na abertura; status calculado — manual override > automático do legado; 148 ativos hoje) → Lista de Distribuição. `vw_dist_precificacao` (finalizados forward-only desde 26/08, ainda não validados; some da lista ao validar) → Precificação. `vw_dist_colab_area` (colaborador × área, a partir de `dist_colaborador_area`) → Painel do Gestor. `vw_fb_os_apontamento` (apontamentos de 1 serviço específico) → detalhe expansível da Precificação. Colaborador nesse módulo = `vw_dim_colaborador` (dimensão do grupo inteiro, filtrada por `situacao='A'`) — **não** é `loja_config_colaborador` (aquele é só Pátio/Tapeçaria do setor antigo).
- **Vendas sem faturamento:** `vw_vendas_sem_faturamento` (VENDA vem do snapshot `rep_vendas_sem_faturamento`; O.S. é **ao vivo**, calculada direto de `vw_os_base.fl_faturada` desde 18/08 — some da lista no mesmo ciclo do comercial, sem defasagem de 30min) + `vendas_sem_fat_followup` (CRUD anon direto). Tela restringe direto na base a O.S. `tipo_saida=NORMAL` + Venda `tipo_saida=LOJA` (exclui DISTRIBUICAO/ONLINE — não é operação de loja física), abre por padrão em "Últimos 30d". `status` (F=Finalizada/A=Aberta) é o andamento do serviço da OS — **diferente** de faturada (critério da lista inteira).

## Arquitetura
- **Padrão de tela:** página em `src/pages/` é fina (repassa `filters` do `AppShell`) e delega pra um componente pesado em `src/components/dashboard/` (ex: `ServicosPatio.tsx` ~250B → `PatioTab.tsx` 20.9KB). Não é placeholder — é o padrão do projeto inteiro.
- **Duas vias de dado:** views leves via `supabase.from()` direto (tipadas em `types.ts`, schema **compartilhado com outros apps Bononi** — `loja_*`/`taco_*` não estão tipadas nele). Views comerciais pesadas (Vendas/Serviços) passam pela **Edge Function `fetch-comercial`** (fora deste repo) via `fetch()` cru + anon key.

## Dívidas e armadilhas conhecidas
- Anon (publishable) key hard-coded — no `client.ts` **e duplicada** em `useComercialData.ts:101` e `ConfigColaboradores.tsx:18` — padrão do grupo (exposição por design), mas as 3 cópias precisam ser trocadas juntas se a key rotacionar.
- `loja_config_colaborador` é a fonte de setor/colaborador da loja (padrão Bononi: **não** usar `departamento` do ERP p/ filtrar setor). Tela fonte de verdade: `ConfigColaboradores.tsx`.
- `INTERNAL_CLIENTS` (`ComercialVendedoresTab.tsx:19-24`) — lista hardcoded de ~27 clientes internos excluída dos rankings de vendedor/cliente.
- `vw_os_res_fat` é o totalizador **oficial** de faturamento de OS — usar essa view, não somar peças+serviços na mão.
- KPI "vs mês ant." em Vendedores na verdade compara com a **média dos 3 meses anteriores**, não o mês anterior simples.
- Tacógrafo: `status` no banco é só `ABERTA`/`CONCLUIDA` (muda só no clique manual "Concluir OS"); os badges `PEND_DOC`/`DOCS_OK` na lista são **derivados/cosméticos**, não refletem coluna do banco. `numero_os` é gerado client-side (maior + 1) — risco de corrida em concorrência.
- `src/data/mockData.ts` não tem mock data — só tipos (`DashboardFilters`) e formatters; nome ficou desatualizado mas é código vivo.
- Clone git é raso (só 2 commits locais) — histórico anterior do projeto não está disponível localmente.
- `vw_vendas_sem_faturamento` deu **timeout no anon role** (`statement_timeout=3s`) até 18/08 — a view faz subquery correlacionada por linha em `vw_dim_cliente` (71.842 linhas, sem índice em `id_cliente`) e `vw_dim_vendedor`. Corrigido com `CREATE INDEX ON vw_dim_cliente(id_cliente)` / `vw_dim_vendedor(id_vendedor)` (migração `idx_vw_dim_cliente_vendedor_id_lookup`). Se voltar a dar timeout depois de a view crescer mais, comece por aqui.
- O projeto Supabase tem um teto de **"max rows" no PostgREST** (retorna no máx. 10000 por request, mesmo pedindo `.range()` maior) — `useQuery` da tela pagina em lotes de 1000 até esgotar. Se outra tela algum dia buscar uma tabela/view que passe de 10k linhas, lembrar desse teto (não é bug do Supabase, é config do projeto).
- Gestão de Serviços não tem login/autenticação própria (mesmo padrão anon-key do resto do app) — "quem distribuiu"/"quem está distribuindo" reaproveita o campo de nome já usado em Vendas sem Faturamento (`localStorage["loja_usuario_nome"]`, chave `USUARIO_KEY` em `src/lib/dist.ts`), não é usuário autenticado de verdade.
- Gestão de Serviços — "Duplicar" cria uma linha NOVA em `dist_servico` com `duplicado_de = id da origem` (não edita a original); a Lista mostra "(dup.)" ao lado do nº do serviço pra diferenciar.
- Gestão de Serviços — colaborador nas telas de distribuição/precificação/painel vem de **`vw_dim_colaborador`** (dimensão do grupo inteiro, filtro `situacao='A'`, ~110 ativos), **não** de `loja_config_colaborador` (esse é só Pátio/Tapeçaria do módulo Serviços antigo — módulos diferentes, fontes diferentes, não confundir).
- Gestão de Serviços — área efetiva numa linha de `vw_dist_servicos`/`vw_dist_precificacao` = **override manual (`dist_servico.id_area`) se existir, senão o mapa automático (`dist_area_servicop`)** por `id_servicop`. `area_automatica=true` avisa quando a área mostrada veio do mapa, não de uma distribuição manual. `dist_area_servicop.id_servicop` é **unique** — um código de serviço só pode cair automático numa área por vez (ao configurar em Config › Áreas, o picker já esconde código que já está mapeado em qualquer área).
- Gestão de Serviços — Precificação: `id_dist` pode vir `null` mesmo pra serviço já finalizado (nunca foi tocado em Destinar/Parar) — `PrecificacaoTab.tsx` trata isso: se `id_dist` existe faz `UPDATE dist_servico`, senão `INSERT` só com os campos de validação.
- Gestão de Serviços — Painel do Gestor "Colaboradores por área" depende de `dist_colaborador_area` estar populada (Config › Áreas → aba "Colaboradores da área"); enquanto ninguém configurar, a seção fica vazia — é o estado esperado, não é bug.
- Gestão de Serviços — **`vw_dist_servicos.observacao`/`vw_dist_precificacao.observacao` hoje não trazem texto de verdade** (achado 26/08): das 1761 linhas, 1413 vêm NULL e 348 vêm com a string de erro do driver Firebird `*** blr version ... is not supported ***` — zero com observação legível. Causa provável: `TBL_SERVICO.DESCRICAO` no Firebird é `BLOB SUB_TYPE BLR` (formato binário interno, não texto de usuário); o campo certo pra observação do vendedor parece ser `TBL_SERVICO.DESCRICAO_IMP` (`BLOB SUB_TYPE TEXT`). Reportado pro cérebro trocar o campo na extração. Enquanto isso, `limparObservacao()` em `src/lib/dist.ts` esconde a string de erro (não deixa vazar pra tela) — mas a observação real só aparece depois do fix na origem.
- **`useSortable` (hook compartilhado, `src/hooks/useSortable.ts`) tinha um bug real de ordenação por string** (achado 26/08 ao ordenar a coluna Data/Hora da Lista de Distribuição): o cálculo tentava `Number(valor) || 0` pra decidir se comparava como número, e como string não-numérica vira `NaN → 0` pros dois lados, a comparação virava sempre `0 - 0 = 0` — a seta do cabeçalho trocava de direção mas a lista **não reordenava**. Isso afetava qualquer coluna de texto/data ordenável no app (`data_venda`/`cliente`/`vendedor`/`empresa` em Vendas sem Faturamento, `cliente` no Gerencial, etc.) — corrigido na raiz (só entra no branch numérico se os dois valores forem numéricos de verdade; senão usa `localeCompare`, que já ordena certo string ISO de data). Testado nas duas telas depois do fix, sem regressão.
- Gestão de Serviços — Lista de Distribuição e Precificação mostram **só OS da MLB PR** (`id_empresa=2`, `EMPRESA_MLB_PR` em `src/lib/dist.ts`) — pedido do Leo 26/08, piloto do módulo. TRUCKPREST/SANTA TEREZA ficam de fora por enquanto. Config › Áreas (catálogo de código de serviço) e Painel do Gestor (fila por área) **não** filtram por empresa — não foi pedido pra esses.
- Gestão de Serviços — **colaborador com fallback pro apontamento do legado**: quando um serviço já está "em serviço" mas nunca foi destinado por aqui (`dist_servico_colaborador` vazio), `DistribuicaoListaTab.tsx` busca o colaborador em `vw_fb_os_apontamento` (quem já apontou hora no serviço) e mostra com a marca "(apontamento)" — não confundir com uma distribuição de verdade feita na tela. Mesma lógica reaproveitada no dialog "todos os serviços da OS".
- Gestão de Serviços — Lista de Distribuição: colunas Data e Hora viraram uma coluna só "Data/Hora" (`dataHora` = `data_os + "T" + hora_os`, ordenável via `useSortable`/`SortableHeader`, mesmo padrão de outras telas do app). Clicar numa linha (fora dos botões de Ação e do chevron de expand, que têm `stopPropagation`) abre um dialog com **todos os serviços daquela OS** (mesmo `id_os` + `id_empresa` — nº de OS repete entre empresas), cada um com seu status e colaborador(es) — não busca de novo no banco, filtra a lista já carregada em memória.
- Tacógrafo — dossiê PDF (`taco-pdf.ts`): fotos (`FOTO_TACOGRAFO*`/`DISCO_*`) já vêm comprimidas no upload (`comprimirImagem`, maxDim 1600, JPEG q=0.82), mas PDF anexado (CRLV/comprovante) é copiado **cru** com `pdf.copyPages` — é o maior risco de estourar o teto de 10MB do dossiê final. Por isso o upload de PDF (não-imagem) trava em 8MB (`MAX_PDF_ANEXO_MB` em `TacografoOrdem.tsx`) e o `gerarDossiePdf` checa o tamanho final e lança erro amigável se passar de 10MB — não tenta recomprimir automaticamente (pdf-lib não faz downsampling de página copiada).
